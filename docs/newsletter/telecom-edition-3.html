Deep Dive: 5G Core AI and Agentic Network Operations

The Agentic NOC Has a Data Problem. NWDAF Wasn't Built for LLM Reasoning.

Vinit Metange · ~10 min read 3GPP TS 23.288 Nokia AN Agent Library NWDAF · Agentic AI

Nokia launched its Autonomous Networks Agent Library at DTW Ignite 2026 on June 23. NVIDIA followed with a reference stack for trusted 24/7 telecom AI agents. Both assume agents can query network state in real time. The analytics layer they rely on is NWDAF, defined in 3GPP TS 23.288. NWDAF's data contract was designed for rule-based NF consumers, not for LLM reasoning loops. That mismatch is the production problem nobody at DTW26 named out loud.

The Lead

The Agentic NOC Is Being Built. Its Data Substrate Isn't Ready.

Nokia shipped its Autonomous Networks Agent Library at DTW Ignite in Copenhagen on June 23, 2026. The library delivers pre-built AI agents covering network assurance, security operations, and service management. Nokia claims 60 to 80 percent productivity gains in root-cause diagnostic cycles, compressing mean-time-to-resolution from hours to minutes. An expanded Nokia-Google Cloud partnership layers Gemini multimodal models into the network operations stack as a reasoning layer across six specialized telecom agents.

NVIDIA's DTW Ignite 2026 showcase presented a complementary picture: a data, model, simulation, and secure runtime stack for building agentic workflows in telecom operations, framed around trusted AI agents that can run continuously, respond to network events, and act within defined operational boundaries.

Both announcements mark the same inflection point: the transition from AI-assisted optimization (a scheduled workload that improves a parameter) to AI agents that respond to events, reason over network state, and take or recommend action in near-real time. That is not a cosmetic rebranding. Agents have different latency requirements, different data access patterns, and different trust requirements than optimization pipelines.

What neither announcement addressed: where those agents get their ground truth about network state, and whether the current data infrastructure of the 5G core is actually fit for the access patterns agentic reasoning requires.

Deep Dive

What NWDAF Provides, and What It Can't

NWDAF (Network Data Analytics Function) is the intelligence layer of the 5G System. Defined in 3GPP TS 23.288, it collects data from every Network Function via the DCCF (Data Collection and Coordination Function) and the UDR (Unified Data Repository), trains analytics and ML models through its MTLF (Model Training Logical Function), and serves results to consuming NFs via the Nnwdaf service-based interface through its ANLF (Analytics Logical Function).

What NWDAF can produce in a live 5G core is genuinely impressive and underappreciated. Per 3GPP TS 23.288 Rel-17, NWDAF analytics IDs cover per-UE mobility patterns, network performance metrics per slice and per area, load predictions for NFs and slices, UE communication characteristics, anomaly detection at the network and device level, and service experience predictions per application and per slice. In commercial deployments from Nokia, Ericsson, and Huawei, these analytics IDs are subscribed to by the PCF (Policy Control Function) and AMF (Access and Mobility Management Function) as direct policy inputs.

The output contract is clean and well-specified. An Nnwdaf response delivers: an Analytics ID, a target NF or area, a result payload, a confidence level, and a timestamp. A PCF receiving a slice load prediction above a threshold maps it to a QoS policy adjustment. An AMF receiving a UE mobility prediction pre-positions resources for a handover. These closed-loop automations have tight, standards-defined input-output contracts. They work.

An LLM agent reasoning about an active network degradation event needs something categorically different, across three dimensions that the current Nnwdaf interface was not designed to address.

The Three Gaps That Matter in Production

5G Core NFs AMF · SMF · PCF · UDM · UDR · RAN PM counters · OSS alarms · BSS context
NWDAF (3GPP TS 23.288) ANLF + MTLF + DCCF: analytics IDs, load predictions, anomaly scores via the Nnwdaf SBI
DATA CONTRACT GAP No standard for multi-source correlation, temporal alignment, or provenance at the LLM reasoning layer
Agent Orchestration Layer Nokia Agent Library · NVIDIA telco agents · LLM reasoning loop · closed-loop actions

Gap 1: Multi-source correlation. Diagnosing a customer-impacting degradation event requires correlating NWDAF analytics (load predictions, anomaly scores) with RAN PM counters from the element management system, OSS alarm data, and topology context from inventory. NWDAF provides one slice of that picture via one interface. Assembling multiple analytics streams into a coherent context window for an LLM has no standardized interface today. Each vendor provides a proprietary aggregation layer.

Gap 2: Temporal alignment. NWDAF analytics are produced asynchronously at configurable reporting intervals. An LLM reasoning loop needs a coherent snapshot of network state at a specific moment, drawn from sources with different data freshness. Without an explicit temporal contract across those sources, an agent risks reasoning over data from different time points. Errors introduced by that misalignment are not surfaced by the Nnwdaf interface. They look like fresh data.

Gap 3: Provenance and uncertainty at the reasoning layer. When NWDAF returns a congestion prediction with confidence 0.78, the Nnwdaf interface delivers that number and stops. An LLM agent needs the answers to questions the interface cannot answer: trained on how much historical data? Over what time window? How does the confidence figure behave under traffic conditions that differ from the training distribution? The spec carries the number; it does not carry its semantics.

Key spec reference: 3GPP TS 23.288 Rel-17 (NWDAF architecture with ANLF and MTLF separation; Nnwdaf service interface definition). Rel-18 adds DCCF and ADRF (Analytics Data Repository Function) to scale data collection and enable model sharing across NF instances. Rel-19 extends normative scope to AI/ML model lifecycle management: model registration, discovery, and transfer between network NF instances. None of these releases define an interface for multi-source context assembly or temporal alignment for agent reasoning workloads. That gap is currently out of scope for both 3GPP SA2 and O-RAN WG2.

The Research Framing That Points in the Right Direction

EURECOM published Agentic-NWDAF in 2026, proposing an orchestration layer that uses MCP (Model Context Protocol) to translate natural language intents into valid NWDAF analytics service calls. The idea is structurally correct: if you can map "predict load on slice 3 in sector B over the next 15 minutes" to a correctly formed NWDAF analytics request with the right Analytics ID, filter parameters, and reporting interval, an LLM can use NWDAF as a callable tool and maintain grounded reasoning. A complementary paper on arXiv (2606.11877) formalizes the LLM-NWDAF integration architecture with an explicit API layer between the LLM agent and the NWDAF service interface.

Both are prototypes, not production interfaces. The translation from natural-language operational intent to valid NWDAF analytics IDs and filter parameters covers a non-trivial combinatorial space. An NOC agent that can ask 50 different operational questions needs to map each of them to the correct Analytics ID subset from 3GPP TS 23.288 Annex A. That mapping layer is neither small nor static as the spec evolves.

The Proprietary Integration Problem in Practice

Nokia's "glass box autonomy" framing for the Agent Library suggests that agents surface their decision trails for operator inspection. That is correct practice and an important governance signal. But the data substrate those agents query is a proprietary integration layer built on Nokia's own network management stack, not a standards-defined interface. An operator with a non-Nokia RAN and a Nokia 5G core cannot run Nokia's agents over both domains with the same data contract.

Nearly every large operator runs a multi-vendor network. An agentic NOC that covers only the single-vendor perimeter is not an autonomous network. It is an automated silo with an LLM in the middle. The productivity claims look worse once that scope boundary is explicit.

Operators with multi-vendor networks (which describes nearly all of them at scale) get fragmented agent coverage by default: Nokia agents for the Nokia domain, Ericsson agents for the Ericsson RAN, with a human or a custom integration script bridging the two. That architecture defeats the purpose of autonomous operations at the NOC level.

One Thing to Know

The Productivity Claim Has a Scope Condition Nobody Is Disclosing

Nokia's 60 to 80 percent productivity gains from the Autonomous Networks Agent Library are credible for narrow, well-scoped operational tasks in a homogeneous Nokia environment. A root-cause agent trained on historical Nokia fault patterns, operating over a Nokia-managed domain, can outperform a human doing the same lookup in an alarm management system. Those conditions almost certainly describe the benchmark environment. The moment the agent must correlate Nokia core analytics, non-Nokia RAN performance data, and BSS context from a separate data model with its own schema, the productivity advantage shrinks faster than the press release implies. Ask vendors to disclose the scope conditions for any autonomy productivity claim before those numbers inform a business case or a board presentation.

Vinit's Take

The Data Contract Is the Product

My Take

The agentic NOC is not a model problem. Nokia has models. NVIDIA has runtime. Google Cloud has Gemini. The bottleneck is the data contract between network intelligence systems (NWDAF, RAN PM counters, OSS alarm feeds, BSS context) and the reasoning layer above them. Until that contract is standardized, or at minimum harmonized across vendor domains, every operator deploying agentic AI is building a proprietary integration layer and calling it intelligence. The EURECOM Agentic-NWDAF work and the LLM-enabled NWDAF research on arXiv are asking the right question. What I am watching: whether 3GPP SA2 or TM Forum picks this up as a formal work item before Nokia and Ericsson lock operators into competing data substrate implementations. Whichever vendor defines the data contract for the agentic NOC will own an infrastructure dependency more durable than the agents running on top of it.
